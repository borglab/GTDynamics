01 / System map

Three runtimes, one shared trajectory.

Each browser connection owns one C++ optimizer process. The browser sends small commands and receives complete trajectory snapshots; the graph and its numerical optimization stay in native code.

OWNERSHIP

The graph lives in C++.

The native process owns robot kinematics, factors, optimized values, damping state, and the iteration counter. JavaScript schedules work and displays results.

ISOLATION

The session is disposable.

There is no shared global graph or saved session database. Reloading reconnects to a fresh optimizer. The UI requires rebuilding a graph after a connection loss.

02 / Build, solve, replan

The buttons change different things.

Start and goal are full six-degree-of-freedom tool poses. Translation handles move them in world coordinates; rotation handles work in the selected frame’s local axes. Numeric position and XYZ Euler controls provide the same edits.

01 · BUILD

Create the problem.

Choose intermediate states and duration. C++ constructs the factors, initializes every slice, and returns iteration zero. No solver step runs yet.

02 · SOLVE

Improve the estimate.

The bridge repeatedly requests one native LM iteration. Every returned snapshot updates the trajectory, error plot, and iteration history.

03 · PLAY

Execute an estimate.

MuJoCo follows the chosen trajectory in the browser. Playback may continue while new optimizer snapshots arrive.

The default is 10 intermediate states over 4 seconds. Native validation allows 1–40 intermediate states and 0.5–20 seconds. An optimizer instance can take at most 80 LM steps.

The initial estimate uses the home posture with a small sinusoidal variation in the first joint across slices, zero joint velocities, and link poses/twists computed from forward kinematics. It is deliberately unplanned, so the intermediate optimizer snapshots show the trajectory taking shape.

Moving a target preserves useful work.

After a graph exists, a target edit replaces its two endpoint pose priors and creates a fresh LM optimizer around the current values. The topology, state count, and duration stay fixed. This warm start avoids rebuilding the trajectory from the initial posture.

During playback, the default “Replan when frames move” option attaches solve: true to target updates. Updates are throttled to roughly one every 150 ms, with the most recent poses included. With playback paused, targets update the graph and the user chooses when to solve.

Discretization is different from a target edit. Changing the number of intermediate states or the duration changes the problem’s time grid. The UI pauses playback, stops solving, and requires Rebuild graph. A new build also resets the recorded iteration history.

03 / Messages & ordering

A small protocol keeps the UI responsive.

The browser sends JSON over /socket. Node translates those messages into newline-delimited JSON (NDJSON) requests on the child’s standard input. Every native request receives a monotonically increasing request_id; C++ echoes it in exactly one response. Native diagnostics go to standard error so they cannot corrupt the data stream.

Browser commandNative operationResult
buildbuild with intermediate-state count, duration, start, and goalbuilt: graph counts and initial trajectory.
solveRepeated iterate commands, one at a timeiteration snapshots plus solver status.
targetstargets replaces endpoint priors; optionally resumes iteratetargets: unchanged estimate, new costs, reset iteration counter.
stopNo native stop command; stop scheduling iterations and invalidate older repliesstatus confirms the pause. An in-flight native step is allowed to finish.
Connection / describedescribedescription: home joints, names, limits, endpoint poses, TCP convention, and solver bounds.

What happens when an edit overtakes a solve?

The bridge serializes native commands. Each build, target replacement, or stop advances a generation counter. A returned iteration is shown only if it still belongs to the current generation and solving remains enabled. Pending target messages are coalesced to the newest one.

Inspect the wire format and snapshot fields

Poses use a world position and a normalized quaternion ordered [x, y, z, w]. The native parser validates numeric bounds and rejects invalid or non-finite inputs.

  "quaternion": [1, 0, 0, 0] }, "solve": true }

04 / Inside the factor graph

A slice contains both joints and links.

05 / How slices connect

Integration gives consistency. Smoothness gives preference.

For each joint, a trapezoidal factor says that the change in angle equals the average endpoint velocity multiplied by elapsed time. Its residual should approach zero:

rq = qk+1 − qk − (Δt / 2)(vk + vk+1)A four-variable scalar factor: two angles and two velocities.

For a moving link, the same idea integrates a body twist on SE(3):

T̂k+1 = Tk Exp[(Δt / 2)(Vk + Vk+1)]
rT = Log[Tk+1−1 T̂k+1]A four-variable six-dimensional factor: two poses and two body twists.

These equations follow the repository’s fixed-time body-twist collocation convention. A separate velocity-change factor favors smooth trajectories:

Esmooth ∝ Σj,k (vj,k+1 − vj,k)² / ΔtThe velocity-difference factor uses σ = √Δt. This approximates the integral of squared joint acceleration.

All terms enter a weighted nonlinear least-squares objective. The graph optimizes q, v, T, and V together; it does not optimize only the visible tool path and then run a separate inverse-kinematics stage.

Noise models, endpoint strength, and the Jacobian implementation

A Gaussian factor contributes ½‖Σ⁻¹ᐟ²r‖². Smaller standard deviation therefore means a stronger penalty. These are soft costs, including kinematics and endpoint priors; no finite weight guarantees an infeasible target can be reached.

Angular residuals use radians; positional residuals use meters. The isotropic six-dimensional pose model assigns the same numeric σ to these different units. It is a teaching-model weighting choice, not a calibrated sensor covariance. Joint-limit costs use GTDynamics’ configured limit model.

Why the app has its own factor header

JointTrapezoidalFactor implements the scalar equation and its four analytical Jacobians. PoseTrapezoidalFactor subclasses GTDynamics’ existing factor, retaining its residual while applying the full Logmap Jacobian chain rule. That derivative matters when a dragged target starts far from the current estimate. test_factors.cpp checks the analytical Jacobians against numerical derivatives.

06 / Two animation clocks

Iteration number is not trajectory time.

CLOCK A · OPTIMIZATION

Which estimate are we viewing?

Each accepted native LM step creates a new whole-trajectory snapshot. The history slider chooses an iteration. Replaying this history shows the path, ghost skeletons, and tool frames evolving toward a solution.

CLOCK B · EXECUTION

Where are we along that estimate?

The arm time slider chooses a time within the selected snapshot. Play advances this clock and drives the physical MuJoCo arm. It can run while Clock A advances, pauses, or is scrubbed.

The bridge’s default 80 ms delay makes optimizer changes visible; actual wall time also includes the native solve step. History replay runs at its own display cadence. Neither controls the robot’s model timestep.

Joint-space Hermite interpolation fills the gaps.

A snapshot contains discrete joint angles and velocities. Between slices, the viewer uses cubic Hermite interpolation, with normalized segment time s ∈ [0, 1]:

q(s) = h₀₀(s)qk + h₁₀(s)Δt vk + h₀₁(s)qk+1 + h₁₁(s)Δt vk+1h₀₀ = 2s³ − 3s² + 1 · h₁₀ = s³ − 2s² + s · h₀₁ = −2s³ + 3s² · h₁₁ = s³ − s²

The viewer also computes the Hermite curve’s analytical velocity, scaled by playback speed and direction. It feeds both desired position and desired velocity to MuJoCo’s position actuators. While playing, mj_step advances the dynamics at the model’s fixed timestep; a wall-clock accumulator determines how many steps to take per rendered frame. Gravity compensation is enabled when loading the model.

The position servo gets velocity feedforward.

Menagerie’s actuator produces kₚ(ctrl − q) − kdq̇. Supplying a raw position target leaves velocity-dependent lag. The viewer offsets the actuator command by the desired velocity:

ctrl = qdesired + (kd / kₚ) q̇desired
⇒ τ = kₚ(qdesired − q) + kd(q̇desired − q̇)The actual command remains subject to the actuator’s control range and a 2.5 rad/s slew limit. Live trajectory replacement preserves MuJoCo joint positions and velocities.

Arrival is a physical check, not just a clock event.

At an endpoint, trajectory time freezes while physics continues integrating, with zero desired velocity. The arm reverses only after its actual TCP is within 0.1 mm and 0.001 rad of the interactive frame and every arm joint is below 0.005 rad/s, continuously for 100 ms. If it cannot settle within 2 seconds, playback pauses and reports that the frame was not reached.

During live playback, changing a frame or replacing the trajectory restarts an active settling deadline without jumping the physical state. Playback speed rescales trajectory time; it does not change the graph’s duration or rerun optimization. Endpoint settling adds physical time beyond the nominal trajectory duration.

Scrubbing is an inspection operation. A direct time scrub, or replacing a snapshot while paused, sets the joint state and calls mj_forward. Continuous Play uses physical integration. The ghost skeletons always show the optimized link-pose variables, including their disagreement with joint kinematics during early iterations.

07 / Reading the errors

A good prior fit and good physical tracking are different.

The red and green targets, the optimized ghost trajectory, and the simulated arm are three distinct objects. Their distances answer different questions. Tightening a Pose3 prior changes the optimization objective; it does not directly increase a MuJoCo actuator gain.

What the UI reportsWhat is comparedHow to interpret it
Graph errorThe sum of all weighted factor costsA unitless objective for comparing iterations of this graph. It is not a distance in millimeters.

Ghost path / link skeletonsOptimized T variables at each sliceThey can temporarily disagree with the arm driven by q while the kinematic factors are still being optimized.

Stopping is not the same as reaching the frames.

The native solver reports done when an error-change criterion or its iteration limit ends the solve. It reports converged only when the error criterion is met and both endpoint FK position errors are below 0.1 mm and rotation errors are below 0.001 rad. targets_reached exposes that endpoint test separately, and the native description publishes the tolerances for the UI.

For an unreachable target, the solver can stop with stalled or iteration_limit and a visible residual. Those thresholds are success-reporting criteria; they are distinct from the much tighter endpoint prior standard deviation.

Physical arrival is checked separately against the interactive red or green frame. It uses those same pose tolerances plus the joint-speed and stable-duration conditions. This check answers whether the simulated hand actually arrived, not just whether the optimized configuration would arrive under forward kinematics.

When the moving hand misses a frame: first inspect the optimized endpoint residuals. If they are small but the moving arm still lags, inspect physical tracking, playback speed, and endpoint settling. If the endpoint residual itself is large, inspect target reachability, conflicting soft costs, or whether the solve has finished.

08 / Coordinates & models

Make the tool frame mean the same thing everywhere.

Both sides use a right-handed, Z-up world in meters and radians. JSON quaternions use [x, y, z, w]. MuJoCo’s native quaternion arrays use [w, x, y, z]; the renderer reorders these explicitly for Three.js. Numeric orientation controls display XYZ Euler angles in degrees, while transport and optimization use quaternions and Pose3.

NATIVE MODEL

URDF → GTDynamics

models/urdfs/panda/panda.urdf is loaded and its fixed links are merged. The graph uses seven named joints and eight links, with link0 fixed. Pose variables are COM frames.

BROWSER MODEL

Menagerie → MuJoCo

The pinned franka_emika_panda model supplies meshes, dynamics, and actuators. Two finger joints are held open; they are not optimization variables.

COM, link origin, hand, and TCP are not interchangeable.

The visible tool center point (TCP) lies 0.1034 m along the Menagerie hand’s local +Z axis. Relative to URDF link7, its transform is translation [0, 0, 0.2104] with rotation Rz(−π/4). The optimizer derives the COM-to-link transform from the loaded robot, then composes the link-to-TCP transform.

TworldTCP = TworldCOM · TCOMTCP
TworldCOM,target = TworldTCP,target · (TCOMTCP)−1Endpoint priors apply to the terminal link’s COM pose after this conversion. Visualization converts COM poses back to link-origin poses.

The asset bootstrap downloads only the Panda model from MuJoCo Menagerie revision a03e87bf13502b0b48ebbf2808928fd96ebf9cf3, writes a manifest, and links the model into the app’s public assets. Its original attribution and license remain in the downloaded model directory.

10 / Run, test, extend

Keep the experiment reproducible.

Use the repository’s normal GTDynamics and GTSAM dependencies, Boost 1.75+ for Boost.JSON, Node.js 18+, npm, Python 3, and Git. From the repository root:

cmake -S . -B build -DGTDYNAMICS_BUILD_STEAP_WEBDEMO=ON
cmake --build build --target steap_optimizer steap_factor_test -j2
python3 steap-webdemo/scripts/bootstrap_models.py
cd steap-webdemo
npm install
npm run dev

Open the local lab on port 3001. Use STEAP_BACKEND=/absolute/path/to/steap_optimizer npm run dev for another build directory. For a remote machine, forward port 3001, for example ssh -L 3001:127.0.0.1:3001 HOST.

Build options and checks

A fresh C++-only configuration can disable unrelated Python bindings and examples with -DGTDYNAMICS_BUILD_PYTHON=OFF and -DGTDYNAMICS_BUILD_EXAMPLES=OFF. Supply your existing dependency prefix using -DCMAKE_PREFIX_PATH=… if needed.

# From the repository root:
ctest --test-dir build -R '^steap_' --output-on-failure
cd steap-webdemo
npm test
npm run build

C++ derivative tests check each collocation Jacobian. Native protocol tests check solving, warm-start retargeting, invalid inputs, unreachable targets, and URDF forward-kinematics agreement. Node tests check stream ordering, cancellation, Hermite interpolation, and its velocity derivative. The real-browser regression checks physical tracking and endpoint settling in both directions at 1×, 2×, and 3×, continuous live trajectory replacement, direct scrubbing, timeout, and recovery. UI smoke testing additionally covers translation, rotation, live replanning during Play, iteration scrubbing, and narrow-screen layout.

To run the browser regression, keep the development server running and provide Chrome plus a Playwright installation. Playwright is a test-only dependency and is not included in the app runtime.

# From steap-webdemo/, with your Playwright module path:
PLAYWRIGHT_MODULE=/path/to/node_modules/playwright/index.mjs \
  node tests/playback.browser.mjs

npm run build produces static browser assets. Running the application still requires its native optimizer and WebSocket bridge; the static bundle alone cannot solve graphs.

What this demonstrates—and what would make it full STEAP.

This app demonstrates STEAP-inspired endpoint replanning with batch Levenberg–Marquardt warm starts. It makes trajectory variables, temporal factors, nonlinear iterations, and replanning visible. It does not add execution measurements back into an estimator or maintain an iSAM2 incremental inference state.

The repository’s gtdynamics/gpmp2/tests/testSTEAP.cpp is the place to inspect its measurement-update/iSAM2 formulation. Extending this app toward simultaneous trajectory estimation and planning would require explicit measurement factors and an estimation/update policy, in addition to changing the optimizer.

Model boundaries matter. The planner includes kinematics, joint-limit costs, temporal consistency, and smoothness. It has no collision-avoidance objective, torque or dynamic-feasibility optimization, or hardware interface. Cubic interpolation and live replacement are not collision or joint-limit proofs between slices. The browser simulation demonstrates execution behavior; it does not certify a motion for a real robot.

A useful classroom sequence

  1. Build with a small number of states and identify the four variable families in each slice.
  2. Run Solve and pause iteration history early: compare the ghost pose trajectory with the solid arm driven by joint angles.
  3. Replay an early estimate and a converged one using the independent arm clock.
  4. Move or rotate a target during playback; trace the prior replacement and warm-start sequence.
  5. Move the goal beyond reach and distinguish “the solver stopped” from “the endpoint was reached.”
